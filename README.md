# openbao-plugin-secrets-nats

`openbao-plugin-secrets-nats` is an [OpenBao](https://openbao.org) secrets engine plugin for [NATS](https://nats.io) NKey/JWT authentication.
It generates NATS credentials for operators, accounts and users, stores them in OpenBao and can push account JWTs to a NATS account server.

A similar tool is [`nsc`](https://github.com/nats-io/nsc), but it only stores credentials on disk and relies on manual steps.

## Features

- Manage NATS NKeys and JWTs for operators, accounts and users
- Issue user creds files
- Push account JWTs to a NATS account server, optionally over TLS/mTLS

# Getting Started

The `nats` secrets engine generates NATS credentials dynamically.
The plugin supports several resources, including: operators, accounts, users, NKeys, JWTs and creds, as well as signing keys for operators and accounts.

There is a command structure to create, read, update and delete operators, accounts, users and permissions based on entity paths.
Please read the official [NATS documentation](https://docs.nats.io/running-a-nats-service/configuration/securing_nats/auth_intro/jwt) to understand the concepts of operators, accounts and users as well as the authentication process.
The plugin exposes the following resources:

Resources of type `issue` represent entities that result in generation of nkey and JWTs.

| Entity path                                                   | Description                                                                        | Operations          |
| ------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ------------------- |
| issue/operator                                                | List operator issues                                                               | list                |
| issue/operator/\<operator\>/account                           | List account issues                                                                | list                |
| issue/operator/\<operator\>/account/\<account\>/user          | List user issues within an account                                                 | list                |
| issue/operator/\<operator\>                                   | Manage operator issues. See the `operator` section for more information.           | write, read, delete |
| issue/operator/\<operator\>/account/\<account\>               | Manage account issues. See the `account` section for more information.             | write, read, delete |
| issue/operator/\<operator\>/account/\<account\>/user/\<name\> | Manage user issues within an account. See the `user` section for more information. | write, read, delete |

Resources of type `creds` are read-only user creds files that can be used to authenticate against a NATS server.
User JWTs are not stored: every read signs a fresh JWT from the user's issue and stored nkey, valid for the issue's `credsTTL` (no expiry if unset).

| Entity path                                                 | Description       | Operations          |
| ----------------------------------------------------------- | ----------------- | ------------------- |
| creds/operator/\<operator>/account/\<account\>/user          | List user creds   | list                |
| creds/operator/\<operator>/account/\<account\>/user/\<user\> | Read user creds   | read                |

Resources of type `nkey` are either generated by `issue`s or are imported and referenced by `issue`s during their creation. Writing (importing) them is deprecated and will become read-only in a future release.

| Entity path                                                  | Description                    | Operations          |
| ------------------------------------------------------------ | ------------------------------ | ------------------- |
| nkey/operator                                                | List operator nkeys            | list                |
| nkey/operator/\<operator>/signing                            | List operators' signing nkeys  | list                |
| nkey/operator/\<operator>/account                            | List account nkeys             | list                |
| nkey/operator/\<operator>/account/\<account\>/signing        | List accounts' signing nkeys   | list                |
| nkey/operator/\<operator>/account/\<account\>/user           | List user nkeys                | list                |
| nkey/operator/\<operator>                                    | Manage operator nkey           | write, read, delete |
| nkey/operator/\<operator>/signing/\<key\>                    | Manage operator signing nkeys  | write, read, delete |
| nkey/operator/\<operator>/account/\<account\>                 | Manage accounts' nkey          | write, read, delete |
| nkey/operator/\<operator>/account/\<account\>/signing/\<key\> | Manage accounts' signing nkeys | write, read, delete |
| nkey/operator/\<operator>/account/\<account\>/user/\<user\>   | Manage user nkey               | write, read, delete |

Resources of type `jwt` are either generated by `issue`s or are imported and referenced by `issue`s during their creation. Writing (importing) them is deprecated and will become read-only in a future release.

| Entity path                                               | Description           | Operations          |
| --------------------------------------------------------- | --------------------- | ------------------- |
| jwt/operator                                              | List operator JWTs    | list                |
| jwt/operator/\<operator>/account                          | List account JWTs     | list                |
| jwt/operator/\<operator>                                  | Manage operator JWT   | write, read, delete |
| jwt/operator/\<operator>/account/\<account\>               | Manage accounts' JWTs | write, read, delete |

## ⚙️ Configuration

There are arguments that can be passed to the paths for `issue/` (operator, account, user), `jwt/` and `nkey/`.

### Issues

Issues can be created with an imported nkey. If the nkey is not present during the creation of the issue, a new nkey will be generated.
**Note: if you don't provide any claims for an operator, account or user, the plugin will generate a default set of claims. The default claims are set to "you are not allowed to do anything".**

#### **Operator**

| Key               | Type        | Required | Default | Description                                                                                                              |
| ----------------- | ----------- | -------- | ------- | ------------------------------------------------------------------------------------------------------------------------ |
| syncAccountServer | bool        | false    | false   | If set to true, the plugin will push the generated credentials to the configured account server.                         |
| claims            | json string | false    | {}      | Claims to be added to the operator's JWT. See [pkg/claims/operator/v1alpha1/api.go](pkg/claims/operator/v1alpha1/api.go) |
| tlsCaCert         | string      | false    | ""      | PEM-encoded CA certificate for verifying the account server's TLS certificate. Only needed for a self-signed or private CA; otherwise the system CA pool is used. |
| tlsClientCert     | string      | false    | ""      | PEM-encoded client certificate for mTLS authentication to the account server. Must be set together with `tlsClientKey`.  |
| tlsClientKey      | string      | false    | ""      | PEM-encoded client private key for mTLS authentication to the account server. Write-only: never returned on read.        |
| tlsFirst          | bool        | false    | false   | Perform TLS handshake before any NATS protocol exchange. Required when the NATS server uses `handshake_first: true`.     |

#### **Account**

| Key           | Type        | Required | Default | Description                                                                                                           |
| ------------- | ----------- | -------- | ------- | --------------------------------------------------------------------------------------------------------------------- |
| useSigningKey | string      | false    | ""      | Operator signing key's name, e.g. "opsk1"                                                                             |
| revocationsTTL | int        | false    | 0       | Seconds to keep revocation entries for deleted users in the account JWT. 0 keeps them forever.                       |
| claims        | json string | false    | {}      | Claims to be added to the account's JWT. See [pkg/claims/account/v1alpha1/api.go](pkg/claims/account/v1alpha1/api.go) |

#### **User**

| Key           | Type        | Required | Default | Description                                                                                                  |
| ------------- | ----------- | -------- | ------- | ------------------------------------------------------------------------------------------------------------ |
| useSigningKey | string      | false    | ""      | Account signing key's name, e.g. "ask1"                                                                      |
| credsTTL      | int         | false    | 0       | Lifetime in seconds of the creds returned by `creds/`. 0 issues creds without expiry.                         |
| claims        | json string | false    | {}      | Claims to be added to the user's JWT. See [pkg/claims/user/v1alpha1/api.go](pkg/claims/user/v1alpha1/api.go) |

### Nkey

| Key  | Type   | Required | Default | Description                                           |
| ---- | ------ | -------- | ------- | ----------------------------------------------------- |
| seed | string | false    | ""      | Seed to import. If not set, then a new one is created |

### JWT

| Key | Type   | Required | Default | Description                                          |
| --- | ------ | -------- | ------- | ---------------------------------------------------- |
| jwt | string | false    | ""      | JWT to import. If not set, then a new one is created |

### 📤 System account specific configuration

This section describes the configuration options that are specific to the system account.

The system account is always named `sys` and the user that pushes account JWTs to the account server is always `default-push`; neither name is configurable. The operator JWT's `systemAccount` claim is set by the plugin, so a value passed in `claims` is ignored.

See the `example/sysaccount` directory for an example configuration of both `sys` account and `default-push` user.

### 🔒 TLS support for account server push

No TLS settings are needed to push account JWTs to a NATS server that requires TLS: the client upgrades the connection when the server asks for it, using the system CA pool. This works with both `nats://` and `tls://` URLs in `accountServerUrl` (`tls://` additionally refuses to connect without TLS).

Set the TLS fields on the operator issue only when you need to customize the connection:

- **`tlsCaCert`** — PEM-encoded CA certificate. Needed if the NATS server uses a self-signed or private CA.
- **`tlsFirst`** — Set to `true` when the NATS server is configured with `handshake_first: true`. Such a server expects the TLS handshake before any NATS protocol exchange, so the client must start with TLS.
- **`tlsClientCert`** / **`tlsClientKey`** — For mTLS, when the NATS server requires a client certificate. Both must be set; they are independent of `tlsCaCert`. `tlsClientKey` is write-only and is not returned when reading the operator issue.

All fields are independent of each other. Invalid PEM input makes the push fail with an explicit error.

```console
$ bao write nats-secrets/issue/operator/myop @example/operator/operator-tls.json
```

See [example/operator/operator-tls.json](example/operator/operator-tls.json) for an example with a private CA and `handshake_first`.

The rest of the setup (sys account, push user, tenant accounts) is identical to the non-TLS flow. Only the operator issue configuration changes.

## 🎯 Installation

### Prerequisites

- OpenBao 2.x with a `plugin_directory` configured
- A NATS server with the [full resolver](https://docs.nats.io/running-a-nats-service/configuration/securing_nats/auth_intro/jwt/resolver) if you want account JWTs pushed automatically

### From a release binary

Download the binary for your platform from the [releases](https://github.com/NatzkaLabsOpenSource/openbao-plugin-secrets-nats/releases) page together with its `.sha256` file and put it into `plugin_directory`, e.g. as `openbao-plugin-secrets-nats`.

Register it declaratively in the OpenBao server configuration (`sha256sum` is optional):

```hcl
plugin_directory = "/etc/openbao/plugins"

plugin "secret" "openbao-plugin-secrets-nats" {
  command   = "openbao-plugin-secrets-nats"
  version   = "v1.10.0"
  sha256sum = "<sha256 of the binary>"
}
```

Or register it manually:

```console
$ bao plugin register -sha256=$(sha256sum openbao-plugin-secrets-nats | cut -d' ' -f1) secret openbao-plugin-secrets-nats
```

Then enable it:

```console
$ bao secrets enable -path=nats-secrets openbao-plugin-secrets-nats
```

### From the container image

Each release publishes an OpenBao image with the plugin preinstalled:

```
ghcr.io/natzkalabsopensource/openbao-plugin-secrets-nats/openbao-with-nats-secrets:<version>
```

Use it in place of `openbao/openbao` and set `plugin_directory = "/etc/openbao/plugins"`. The binary is `/etc/openbao/plugins/openbao-plugin-secrets-nats` and its checksum is in `/etc/openbao/plugins_checksums/openbao-plugin-secrets-nats.sha256`. Register and enable it as shown above.

# 🛠️ Development

Requirements: Go (version from `go.mod`), the `bao` CLI, `docker` and `jq`.

| Command        | Description                                                                         |
| -------------- | ----------------------------------------------------------------------------------- |
| `make`         | Format, build the plugin and start an OpenBao dev server with it on `127.0.0.1:8200` |
| `make enable`  | Enable the plugin at `nats-secrets/` on the dev server                              |
| `make example` | Run the example against the dev server                                              |
| `make test`    | Run unit tests and `go vet`                                                         |
| `make build`   | Build the plugin into `build/openbao/plugins/`                                      |

The dev server's root token is `root`.

## 💡 Example

The `example` directory sets up an operator and a `sys` account, both using signing keys, plus a `default-push` user used to push account JWTs.
It starts a NATS server in docker configured with the generated operator, then creates a regular account and user, and publishes a message with that user's creds.

In one terminal:

```console
$ make
```

In another:

```console
$ export BAO_ADDR='http://127.0.0.1:8200'
$ bao login root
$ make enable
$ make example
> Creating NATS resources (operator and sysaccount)

Success! Data written to: nats-secrets/issue/operator/myop/account/sys

> Generate NATS server config with preloaded operator and sys account settings
> Starting up NATS server
> Creating normal account and user
```

## 🐞 Debugging

Prefer debugging through unit tests. To debug the plugin running in OpenBao, run `make` and `make enable`, attach your debugger to the plugin process (it is built without optimizations) and drive it with the `bao` CLI.
